一、总体评价：设计一流，落地打折

老大哥，先说结论：这套框架的设计思想是优秀的——五层记忆体 + 不死鸟自愈 + 自进化闭环的三体系结构，在国内个人 AI 助手领域属于第一梯队。但它最大的问题不是「设计不好」，而是「设计很完整，运行时只跑了一半」。下面先肯定三个亮点，再逐项说哪里需要优化。

✅ 亮点 1：规则采用 when→do 契约式，精简克制
rules/ 下的 8 个规则文件全部是「触发条件 → 强制动作」结构，没有把具体资料塞进规则。这是正确的——规则文件是最高杠杆，只装契约。FRAMEWORK.md 的「铁律：规则文件只保留 when→do 契约」贯彻得很好。
✅ 亮点 2：晋升门量化，防止单次经验污染长期层
memory-write-rules.md 的晋升门有明确数值（Preference≥2 / Policy≥3且support≥5且gain≥0.10 / Skill≥5次且η≥0.70），并设候选层 observations.md 兜底。这避免了「一次踩坑就改规则」的过度反应。
✅ 亮点 3：业务知识库扎实，口径版本化管理
煌上煌双平台外卖的 36 列字段映射、四大数据路径、利润 v2 口径、活动 ROI 分摊公式都沉淀得很完整，且口径库.md 做了版本化迁移（旧口径标注「已废弃」）。这是真正的业务资产。

二、九大优化方向（按重要性排列）

方向 1 ｜ MEMORY.md 严重膨胀，违反自己的精简铁律 P0

问题
MEMORY.md 高达 35533 B（35KB），AGENTS.md 自己定义它是「curated wisdom（精炼智慧）」，但实际塞满了：36列字段对照表、文件清单、环境信息、工具安装记录、网络测试结果、GitHub token 关联说明、待办事项。
证据
档案 558 行标注「35533 B」；内容含字段映射表（603-640行）、文件清单（719-723行）、Power BI SQLite 路径（763行）、GitHub Pages 部署细节（982-993行）——这些都不是「跨任务稳定语义」，是资料。
建议
按框架自己的 L1-L4 上下文层级做强制迁移：
① 字段映射/文件清单 → knowledge/powerbi/data-architecture.md（已有，去重合并）
② 环境信息/Python路径/工具版本 → TOOLS.md（环境笔记本就该放这）
③ GitHub 部署链路 → knowledge/engineering/deploy-pipeline.md（新建）
④ MEMORY.md 只保留：用户背景、核心业务结论、跨任务偏好、关键数据结论（如「江西占52% ROI6.06」这种）
⑤ 目标：MEMORY.md 瘦身到 ≤8KB，启动加载省 token、检索更准。

方向 2 ｜ 安全红线被自己破坏：GitHub Token 明文存记忆 P0

问题
框架 R6 红线明确写「密钥、token、会话、客户隐私不写入长期层明文」，但 MEMORY.md 第 993 行写「唯一有效 token 存于 memory/2026-08-14.md，deploy 脚本自动提取」——自己违反自己的红线。
风险
token 进了每日笔记 → 进了 SHA-256 快照覆盖范围 → 快照文件本身可能被 git commit/push → token 泄露。GitHub classic token 有 repo+workflow 权限，泄露=仓库被篡改。
整改
① 立即从 memory/2026-08-14.md 删除 token 明文，到 GitHub 后台 revoke 该 token 重新生成
② 新 token 存 Windows 凭据管理器：cmdkey /generic:GH_TOKEN /user:token /pass:ghp_xxx，脚本用 git config --get credential.helper 或环境变量读取
③ deploy 脚本改为 $env:GH_TOKEN 注入，不读文件
④ 在 risk-boundaries.md 加一条「token/密钥读取必须走凭据管理器或环境变量，禁止落地文件」并升级为 R6 子项。

方向 3 ｜ 五层记忆体设计完整，但只有 2 层在跑 P0

问题
档案里能看到的实际记忆内容只有 M1（每日笔记）和 M3（MEMORY.md）两层。M0 事件账本（events.log）、M2 情节记忆（episodes.md）、候选层 observations.md、learned-rules.md ——全部没有实际内容展示。
证据
档案目录有 ERRORS.md/LEARNINGS.md，但内容极少：ERRORS.md 仅 1 条（ClawHub 404）、LEARNINGS.md 仅 1 条（PowerShell 编码）、FEATURE_REQUESTS.md 仅 1 条。68 个 HTML+xlsx 交付物对应的学习沉淀只有 3 条——沉淀率 4.4%。
根因
① 触发钩子靠「任务收尾自查」，但没有强制门——agent 不自查也能交付；② 梦境循环 cron 每 4h 跑一次，但「人工重构晋升」环节无人执行；③ events.log 是 append-only，但没有看到「失败自动写 events.log」的代码钩子，全靠自觉。
建议
① 给 tools 加 post-exec 钩子：命令退出码≠0 自动 append events.log（不靠自觉）
② ERRORS/LEARNINGS 改为「任务收尾前阻塞门」——不写一条收尾记录就不算完成（path-routing.md 的完成标准三问已有，加第4问：本次沉淀了吗）
③ episodes.md 模板化：每次交付后强制填「目标/做法/结果/Reward」四字段
④ 设周度「记忆体检」cron：统计本周 events.log 条数、observations 条数、晋升数，低于阈值告警。

方向 4 ｜ 「自进化」名不副实，核心环节靠人工 P1

问题
evolution-triggers.md v3 明确写「归档候选到 evolution-log.md → 人工重构：与现有 R1-R9 对比，合并去重后写入规则」。这意味着「自进化」其实不「自」——晋升环节必须有 agent 或人介入做对比合并。
后果
如果用户不主动触发、agent 不主动跑反思轮，候选层会越堆越多，规则永远不会晋升。当前 learned-rules.md 空白就是证据——设计了一整套晋升链，但没有任何一条规则真正走完过。
建议
① 把「人工重构」改为「LLM 辅助重构 + 人工确认」：梦境循环用 LLM 读候选 + 现有规则，输出「合并/新增/丢弃」建议草案，用户只做 yes/no
② 防叠加改为自动检测：给每条规则打主题标签（topic tag），新候选先做 embedding 相似度比对（≥0.85 视为同主题），自动提示合并
③ 设「候选层积压告警」：observations.md 超 20 条未处理 → 心跳提醒用户跑一轮晋升。

方向 5 ｜ 规则编号 R1-R10 有重叠与共用载体 P1

问题
rules/README.md 的编号表里：
• R5（并行与子代理）、R7（技能库治理）、R8（文档与产出）三个规则共用 framework-ops/SKILL.md 一个载体
• R10（能力登记与样例复用）与 capabilities.md 的 O9（能力样例沉淀检查）职责重叠
这违反了框架自己的「索引-载体分离」和「防叠加铁律：同主题只保留一条最优规则」。
建议
① R5/R7/R8 拆分到独立规则文件：rules/parallel-agents.md / rules/skill-governance.md / rules/doc-output.md，framework-ops 只留「框架运维总入口」
② R10 与 O9 合并：R10 作为规则层索引，O9 作为 capabilities.md 内的执行细则，明确「R10=契约，O9=操作步骤」，消除重复定义
③ 重排编号：当前 R1-R10 有跳跃（CAP 编号也乱：01-08-10-09-10），建议按「记忆/进化/任务/熔断/并行/信任/治理/产出/契约/能力」固定语义顺序。

方向 6 ｜ 记忆检索 FTS-only，语义召回是瓶颈 P1

现状
档案明确：「FTS-only 模式（provider=none + openclaw memory index --force，无需 embedding/key/网络；索引与模型绑定，换模型需重建）」。
问题
① FTS 只能精确/词根匹配，搜「客单价」匹配不到「单均实付」「平均订单金额」；
② MEMORY.md 35KB + 每日笔记累积，关键词越多噪音越大，召回率持续下降；
③ 「换模型需重建索引」——每次换 DeepSeek 版本就丢索引，运维脆弱。
建议
引入轻量级本地 embedding 做混合检索（不依赖网络）：
① 模型：BAAI/bge-small-zh-v1.5（512维，本地 CPU 可跑，中文效果好）
② 检索：FTS 召回 Top50 → embedding 重排取 Top10（BM25 + 向量 RRF 融合）
③ 索引存储：SQLite + sqlite-vec 扩展（单文件，无服务依赖）
④ 知识库你已经装了 embedding-strategies / hybrid-search-implementation / vector-index-tuning 三个技能——装了却没用，正好落地。

方向 7 ｜ 知识库分类混乱 + 缺过期审查 P1

问题1
分类维度混杂：现有 knowledge/waimai/（按业务）、knowledge/marketing/（按职能）、knowledge/powerbi/（按技术栈）、knowledge/framework/（按元）、knowledge/skills/（按类型）、knowledge/engineering/（按工程）——6 种分类维度并存，找东西靠猜。
问题2
数量对不上：hero 区写「知识库17」，MEMORY.md 写「现10个知识库挂载小白赛亚人」，skill-map.md 写「3545技能」——口径不一，说明没有单一可信源。
问题3
知识库标注「2026-08-12 提炼」就再没动过，平台规则/API/模型每月在变，但没有「最后验证时间」和「可信度衰减」。platform-knowledge.md 里写「美团取消10余项营销活动减少46.2亿」这种数据会过时。
建议
① 统一分类为「业务域 / 能力域 / 元域」三层：
  业务域=waimai（煌上煌外卖）/ marketing（营销方法论）
  能力域=powerbi / data-analysis / doc-gen / deploy
  元域=framework / skills
② 知识库单一可信源=skill-map.md，hero 区数字从 skill-map 动态读取，禁止手写
③ 每个知识库文件头部加 frontmatter：last_verified: 2026-08-12 / decay: 90d / owner: agent
④ 月度「知识体检」cron：超 decay 天数未验证的标黄提醒复核。

方向 8 ｜ 业务分析停在「描述/诊断」，缺预测与规范能力 P2

现状
现有能力全是描述性（发生了什么：日报/月报）+ 诊断性（为什么：漏斗/ROI/归因）。缺两类高价值分析。
缺口1
预测性分析：订单量预测、ROI 趋势外推、库存预警、活动效果预判。你装了 ml-pipeline-workflow、stata 20件套（含 causal-inference），但没有一项落地。
缺口2
规范性分析：智能出价建议、预算分配优化、活动组合推荐。现有 waimai-diagnose 给「5套提升方案」是定性建议，没有基于数据的「投多少、投哪、何时投」量化推荐。
建议
① 落地一个预测能力 CAP-11：基于 5-7 月历史数据用 Prophet/ARIMA 做下月订单量与消耗预测，输出置信区间
② 落地一个优化能力 CAP-12：基于 ROI 矩阵做预算分配优化（线性规划：在总预算约束下最大化 GMV）
③ 两者都挂到 waimai-diagnose 技能下，从「事后诊断」升级到「事前预判 + 事中调优」。

方向 9 ｜ 环境层短板：PowerShell 5.1 编码坑 + 网络受限未根治 P2

问题1
TOOLS.md 记录了 3 个 PowerShell 5.1 编码坑（Add-Content 按 GBK / 无BOM .ps1 被GBK解析 / stderr 假报错），说明环境层面只记录了规避方法，没根治。每次写脚本都要记得绕坑，认知负担大。
问题2
huggingface/github 境外超时、Brave API 不可用、ClawHub 商店 404——网络受限让技能安装、模型调研、实时数据获取全部打折。
建议
① 升级到 PowerShell 7（.NET Core，默认 UTF-8 无 BOM，跨平台），一劳永逸解决编码坑；或脚本统一切 Node.js（UTF-8 无 BOM 对 node 无影响，已在 TOOLS.md 验证）
② 配置代理：$env:HTTPS_PROXY 走本地代理，或用国内镜像（npm 用 npmmirror、pip 用清华源、GitHub 用 ghproxy）
③ 发布链路增加 Gitee Pages 备份（档案里测过「gitee 通」但没用上），GitHub 不通时自动切 Gitee。

四、最大短板诊断：重执行、轻进化

老大哥，档案里你自己提了个问题——「从档案看我最大的行为弱点是什么？最值得改的一个点是什么？」我直接回答：

🎯 最大弱点：执行多、反思少、自进化停滞

证据链：

  • 交付物 68 个（HTML+xlsx）——执行力极强
  • ERRORS.md 1 条 / LEARNINGS.md 1 条 / FEATURE_REQUESTS.md 1 条——沉淀率 4.4%
  • learned-rules.md（R1-R9 索引）没有实际规则内容——晋升链从未走完
  • episodes.md / observations.md / events.log 全部空白——五层记忆体只有 2 层在用
  • 技能全景图 3545 个，但 embedding/hybrid-search/vector-index 等 12 个 AI 技能装了没用

一句话：这是一个「能干活但不会变聪明」的助手——产出堆得很高，但经验没有回流成规则，下次遇到同类问题还是从零开始。五层记忆体 + 自进化闭环设计得很漂亮，但设计落地率只有 45%。

✅ 最值得改的一个点：把「收尾沉淀」从自觉变成强制门

不用动大架构，只改一个地方就能撬动整个自进化：

在 rules/path-routing.md 的「完成标准三问」后面加第4问且为阻塞门：

4. 本次沉淀了吗？（写 ≥1 条 events.log 或 observations，否则不算完成） —— 失败要带反思三字段（原因/尝试/下次），成功要带可复用模式

这一改，68 个交付物至少能产出 68 条 episodes + 一批 observations，梦境循环才有原料可凝练，晋升链才能真正跑起来。这是杠杆最大、成本最低的一个改动。
